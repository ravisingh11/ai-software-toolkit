# v2.3.0 compatibility evidence

This review deepens the four v2.3.0 simplification areas without adding checks or
automating adoption. Checks remain optional, Core advisory, and lifecycle/polyglot
execution manual. The release stays draft pending maintainer review.

## Claims and acceptance boundaries

| Promise | Authoritative source | Falsification | Acceptance evidence |
| --- | --- | --- | --- |
| Correct starter | Seven named starter skills, Core profile, installation contract | Wrong component, skill, client directory, workflow, or policy value | Four fresh CLI consumers; exact names; 11 workflows and 12 advisory Core checks |
| Existing consumers preserved | Published v2.2.1 CLI bytes and consumer ownership records | Changed selection/custom file, added optional workflow, lost ownership, incomplete rollback | Eight locked/unlocked × customized/plain × partial/complete seeds; paired re-init and update/rollback runs |
| Evaluation preserved | Published catalog/provider/profile contracts and evaluator | False pass, stale or wrong subject accepted, inactive checks scored | Identical evidence through both evaluators and scorecards; exact JSON comparison and independent count/decision expectations |
| Doctor remains read-only | Diagnostic boundary; no producer or credential-value access | Ignored/untracked file changes, configured command executed, secret value accessed | Complete consumer snapshots plus existing command/credential/Git-helper sentinel tests |
| Documentation remains accurate | Version 1 documentation mappings and comparison contract | Untracked docs satisfy mappings, dependencies scanned, missing policy/base passes | Existing positive/negative mapping, tracked-file, fallback, symlink and Git-failure regressions in hosted CI |
| Spec Kit remains optional | Archive contract, preset compatibility identifier and explicit source packager | Bundled preset, broken CLI, removed source integration, changed historical assets | Exact archive/source inventories, CLI consumer runs, historical release asset identities/digests |

A catalog count is discoverability evidence, not evidence that its producers ran.
Fixture evidence tests evaluation behavior; it is not a real scanner, lifecycle,
credential-validity, or application-readiness result.

## Baseline and intended differences

Published v2.2.1 source revision: `bf05798e4b03610551f9882620767f31de03d1df`.
The baseline is the actual published `ai-toolkit.pyz` asset (ID `665661829`),
SHA-256 `020949c5a42490db814d9f8867c637530f2f66aa69c9a7d3bb1916315fd82eee`.
Its checksum asset (ID `665661888`) has SHA-256
`99b1f4e6106f64ed07602264b3c3429584d7107fcdd32e873d34902b3fdd467f`.
Both digests and embedded revision are verified before executing the baseline.

Fresh installation defaults intentionally change. Legacy metadata remains absent;
legacy selections, client destinations, workflows and custom files must remain
unchanged. Parsed configuration comparison removes only the distribution revision.
Managed hashes may change for canonical runtime/documentation upgrades; the
comparison permits only exact old-payload to corresponding new-payload bytes.
The only allowed added legacy managed path is `.proof/activation.py`. Every
accepted consumer file difference is recorded with its before/after hash and mode.
Evaluator and scorecard outputs are compared without removing any JSON fields.

Rollback must validate configuration/lock installation-set consistency before
restoring files, deleting newly managed files, or rewriting records. Inconsistent
records also fail in dry-run mode. The regression checks that backups and consumer
files stay byte-identical and the restore function is never reached.

## Hosted replay and inspection

Use the existing **Distribution Acceptance** workflow, whose permissions remain
`contents: read`. It downloads the immutable baseline, runs focused regressions,
builds the candidate archive, and exercises those exact bytes. No real provider
or configured consumer command is executed by the acceptance fixtures.

For a maintainer replay, select the exact reviewed branch/ref:

```sh
gh workflow run distribution-acceptance.yml --repo ravisingh11/ai-software-toolkit --ref REVIEWED_REF
gh run view RUN_ID --repo ravisingh11/ai-software-toolkit --log
gh run download RUN_ID --repo ravisingh11/ai-software-toolkit --name verified-distribution-SOURCE_SHA --dir verified-distribution
```

On a hosted worker, the workflow's acceptance command is:

```sh
python3 tooling/verify_distribution.py --archive dist/ai-toolkit.pyz \
  --legacy-archive ../legacy/ai-toolkit.pyz --revision SOURCE_SHA \
  --output dist/distribution-verification.json
```

The verification record contains baseline identities/digests, exact source and CLI
hash, all consumer transitions and accepted differences, raw paired evaluator and
scorecard outputs with their input policies/evidence, and negative controls for
selection drift, altered custom files, false passing evidence and archive membership.
Profiles, catalog and provider inputs come from the pinned published archive;
`deep-sast` additionally selects `snyk-code` as a supplemental provider for those
fixtures, recorded in the harness. All results must pass before draft refresh.

Retain raw CI logs and required check-run records for the tested head. After merge,
verify its tree matches the reviewed/tested tree, run acceptance on that merged
revision, and package the retained tested CLI rather than rebuilding it locally.
The draft manifest and release notes identify the revision, run, artifact hashes
and observed limits. Download all refreshed draft assets and verify their sizes,
checksums and manifest references. SHA256SUMS covers the manifest but not itself;
the manifest covers content assets without self-referential hashes.

These are asset-integrity and hosted fixture observations, not native build
provenance. No extra local tests, consumer deployment, credential migration,
automatic activation, enforcement change, historical asset replacement or release
publication is part of this review.
