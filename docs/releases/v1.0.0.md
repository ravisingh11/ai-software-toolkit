# Engineering Standards v1.0.0

First stable release of Engineering Standards and its Guardrails runtime.
Run real checks locally or collect trusted GitHub PR results, evaluate them
against repository-owned policy, and get revision-bound evidence and a
readable scorecard. Missing evidence is never a pass.

This release includes the work previously drafted as v0.3.0. The repository
release is **v1.0.0**; the runtime and evidence schema remain **version 2**.
The major release marks the compatibility commitment below, not a claim that
every catalog integration is complete or activated.

## Stable public contract

- `.guardrails/` is the installed runtime/configuration directory. Use the
  documented installer, configurator, scanner, evaluator, and setup doctor.
- Version 2 capability/profile/provider policy and nested exact-subject
  evidence remain compatible with v0.2.0 installations. No schema migration
  or automatic promotion to enforcement is introduced by this release.
- Modes remain `advisory`, `enforced`, and `not_activated`. Missing, skipped,
  stale, and unconfigured producers cannot satisfy an enforced capability.
  AI review is advisory-only.
- Preserve consumer-owned commands, policy, ground-truth and documentation
  mappings; review refresh diffs before committing.
- Incompatible changes to these documented interfaces require a new major
  release and migration instructions. Internal Python helpers are not a public
  library API. Third-party service behavior and credentials remain external.

## Included

- Core install/refresh, Python consumer demo, real local command producers,
  machine-readable evidence, and timestamped Markdown scorecards.
- Trusted exact-head GitHub PR collection with workflow and provider-App
  checks; independent producers, summaries, artifacts, and PR reporting.
- Read-only setup diagnostics via `.guardrails/doctor.py`, including optional
  repository-level GitHub metadata probes. Configuration is not scan evidence.
- Optional aggregate-only scorecard badge publishing, with explicit Pages
  ownership and privacy boundaries.
- Engineering policies, PR review guidance, workflow/ruleset templates, and
  reusable skills. See the [changelog](../../CHANGELOG.md#100---2026-09-17)
  for changes since v0.2.0.

## Install

Requires Git, Python 3.11+, and a POSIX shell. Start with the
[copyable isolated demo](../../README.md#start-here), or install into your own
repository using the [quickstart](../quickstart.md).

```sh
git clone --branch v1.0.0 https://github.com/ravisingh11/ai-software-toolkit.git
cd ai-software-toolkit
python3 tooling/install.py --target /path/to/repo --dry-run
python3 tooling/install.py --target /path/to/repo
```

For automation, pin the reviewed release commit SHA. Release tags are not
intentionally moved; do not depend on a floating `main` reference for a
reproducible installation.

## Upgrade from v0.2.0

From the v1.0.0 checkout above:

```sh
python3 tooling/install.py --target /path/to/repo --refresh-existing --dry-run
python3 tooling/install.py --target /path/to/repo --refresh-existing
python3 /path/to/repo/.guardrails/doctor.py --target /path/to/repo
```

Refresh updates distributed runtime and installer-owned workflows. It retains
consumer policy, documentation/ground-truth mappings, scope/metadata settings,
unmarked consumer workflows, and repository-specific provider trusted paths.
Review custom modifications to installer-owned files; refresh can replace them.
Commit reviewed changes, scan a clean consumer revision, and verify a real PR
before changing branch requirements. Refresh does not activate providers or
change GitHub settings. Doctor may return setup gaps or unverified items.

To roll back, revert the installation-update PR in the consumer repository.
Keep its prior reviewed configuration and runtime together; do not move a
published release tag or overwrite unrelated consumer work.

## Boundaries

- All selected capabilities default to advisory. `ORANGE / ALLOW` is useful
  feedback, not an all-controls-passed result or security certification.
- Core scanner tools require the documented pinned host tools or a working
  Docker runtime. Missing commands/tools and unavailable GitHub evidence
  remain `NO RESULT`. A first commit may lack a comparison base.
- GitHub profile checks need applicable platform settings and access.
  SonarQube, Snyk, Semgrep AppSec Platform, FOSSA, AI review, and other adapters
  need their documented configuration/implementation; installing definitions
  alone does not activate them. See [control setup](../guardrails/control-setup.md).
- Artifact provenance is a release-attestation workflow, not a PR merge check
  or a completed nested-artifact scorecard producer. Artifact, deployment, and
  runtime catalog entries without producers remain evidence contracts.
- The optional latest-PR badge describes an accepted PR evaluation, not the
  current default branch. It does not affect policy decisions.
- This is a source release: use the tag/commit or GitHub's source archives.
  No built binaries, separate Spec Kit preset ZIP, or attested release artifact
  are distributed. The legacy preset packaging helper is not a supported
  release path; its source-directory reference needs repair before use.

## Verification

Candidate verification on 2026-09-17 used Python 3.14.6: all 395 repository
tests and 20 distributed-skill tests passed, along with build, lint, and the
repository, documentation, demo, and no-migrations validators. The upgrade
smoke from the actual v0.2.0 source preserved policy and ground-truth mappings,
installed the doctor, and passed demo build/unit tests. Its `ORANGE / ALLOW`
scorecard kept missing and remote-only providers visible; it was not an
all-catalog pass. The release page records the final commit and PR evidence.

Run the [complete validation suite](../../AGENTS.md#verification) against the
release candidate, plus the [consumer lifecycle tests](../../tooling/tests/test_consumer_lifecycle.py).
These cover real failures, advisory versus enforced behavior, recovery, missing
commands, and configuration-preserving refresh. Inspect the release PR's CI
and scorecard before publication; a green workflow alone is not an all-green
scorecard.
