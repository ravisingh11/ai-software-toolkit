# v0.3.0 release notes — draft

**Unreleased. Do not treat this document as a tag, publication, or acceptance
record.** v0.2.0 remains the latest actual release. Guardrails v2 is the runtime
contract name and is distinct from the repository release version.

## Intended outcome

Make the first install understandable and diagnosable without treating
configuration as execution evidence. The README leads with a release-pinned
Python demo and links to detailed onboarding, an explicitly illustrative
scorecard, and one canonical badge-setup guide.

## Changes since v0.2.0

Already present in source history: stronger exact-head GitHub evidence and
provider-App matching, repository-owned producer activation, guardrail
change-workflow skills, and optional aggregate-only scorecard badge publishing.
See the [changelog](../../CHANGELOG.md#unreleased) for the release boundary.
These additions are not retroactively part of the v0.2.0 installer.

Implemented, unreleased diagnostics are distributed as `.guardrails/doctor.py`, including
runtime-only installs, and added by refresh:

```sh
python3 .guardrails/doctor.py
python3 .guardrails/doctor.py --target /path/to/repo --json
python3 .guardrails/doctor.py --github OWNER/REPO
python3 .guardrails/doctor.py --operation release
```

`--target` defaults to the current working directory; `--operation change|release`
defaults to `change`. `--json` returns
machine-readable diagnostics. Optional `--github OWNER/REPO` performs read-only
metadata probes using the authenticated `gh` CLI. There is no implied GitHub
probe without this opt-in. The probes inspect repository-level Actions variables
and secret names, plus secret-scanning/push-protection settings when that provider
is selected. Inherited organization/environment variables and secrets are not
queried; token validity, permissions, and workflow availability are not verified.

Setup states are `configured` (inspected prerequisites present, not executed),
`action_needed` (actionable setup gap), and `unverified` (readiness cannot be
established by these checks). Exit **1** indicates actionable gaps, including
readable but invalid installed configuration; **0** means none were found but
can include unverified items; **2** indicates invalid CLI arguments, a nonexistent
target, or failure to load a required runtime helper. Exit 0 does not certify
passing controls.

Doctor does not execute scans or configured commands, install tools, or mutate
files, configuration, secrets, or GitHub settings. Local **configured** is not
**passed**. Unavailable credentials, permissions, tools, or metadata must remain
visible limitations. Neither diagnostics nor metadata replace revision-bound
scan and PR evidence.

Git inspection disables hooks, fsmonitor, and filters and skips submodule
recursion: an otherwise clean checkout with `.gitmodules` remains `unverified`,
and filtered files may appear dirty. Review `git status` in a trust-reviewed
checkout, including filters and submodules, before scanning; do not discard work
to clear this diagnostic.

## Upgrade from v0.2.0

Use an explicitly reviewed checkout containing the v0.3.0 changes for
pre-release evaluation; there is no v0.3.0 tag to clone yet. From that checkout:

```sh
python3 tooling/install.py --target /path/to/repo --refresh-existing --dry-run
python3 tooling/install.py --target /path/to/repo --refresh-existing
```

Review the plan and resulting diff. Refresh updates distributed runtime and
installer-owned workflows while preserving consumer policy, documentation and
ground-truth mappings, scope/metadata configuration, and unmarked consumer
workflows. Provider contracts are refreshed while preserving repository-specific
trusted-path additions. Refresh is not a replacement for reviewing custom
changes inside installer-owned files.

Commit the reviewed changes before scanning a clean consumer `HEAD`. Keep
capabilities advisory until their real producers, exact-head evidence, stable
check names, and owners are verified. Upgrading files does not enable platform
settings or branch protection.

The publisher is optional: follow
[badge setup](../quickstart.md#publish-the-optional-scorecard-badge).
Dedicated mode owns the entire Pages deployment; integrate into the existing
site's workflow instead when Pages is already in use. The public projection
excludes detailed evidence. The latest PR badge does not attest current `main`
and never changes the merge decision.

## Validation on 2026-09-17

- All 393 tests in the runtime, tooling, validator, and demo suites passed.
  The 20 distributed-skill tests also passed. Changed production lines have
  100% coverage against `origin/main`.
- Build, Ruff/yamllint, repository/documentation validators, and the
  no-migrations check passed. The pinned Semgrep 1.175.0 container scanned
  56 targets with the repository rules and reported no findings; its positive
  and negative fixture test passed after fixing the ignored test-directory path.
- Fresh-consumer tests cover real failures, advisory versus enforced outcomes,
  repair, missing commands, and idempotent configuration-preserving refresh.
  A separate consumer installed from the actual v0.2.0 tag was upgraded and
  produced a clean, revision-bound `GREEN / ALLOW` for its selected build,
  test, and ground-truth capabilities. This is not an all-catalog claim.
- Diagnostic tests cover source/installed execution, runtime-only installation,
  Git hooks/filters, unsafe configuration names, subprocess failure, malformed
  metadata, and read-only GitHub probes. A live GitHub probe verified observable
  repository configuration, not producer execution or secret values.

## Constraints and publication

- The exact README v0.2.0 shell block was executed end-to-end on 2026-09-17:
  install preview/refresh, configuration, temporary-repository commit, and scan
  completed. Build and all five unit tests passed; overall `ORANGE / ALLOW`
  was not an all-controls-pass. Semgrep reported that its rules path did not
  exist; container mount visibility was not independently checked, so the cause
  remains unverified. First-commit scope/documentation checks lacked
  `HEAD~1`, and unconfigured/remote producers remained no result.
- The README's v0.2.0 walkthrough cannot run the new doctor or publisher options.
- Local build/test success depends on real commands and a clean committed
  revision. Missing scanners, commands, or GitHub-only evidence remain no result.
- Artifact provenance is release-attestation-only, not a PR required check or
  fully runnable nested-artifact scorecard producer.
- The four-color sample is an illustrative fixture, not a live acceptance run.
- Before publishing a tag, rerun the [validation suite](../../AGENTS.md#verification)
  and GitHub checks for the exact release commit. Local candidate validation
  does not substitute for that release-commit acceptance.
- The three [consumer lifecycle tests](../../tooling/tests/test_consumer_lifecycle.py)
  exercise actual install/configure/commit/scan behavior: a real failing test
  remains advisory, blocks after enforcement, survives refresh, and passes
  after repair; an absent command is not run or passed and blocks when enforced;
  repeated merge/refresh preserves consumer configuration, outcomes, and
  worktree cleanliness. Run them with
  `python3 -m unittest tooling.tests.test_consumer_lifecycle -v`.
- No tag, release publication, deployment, or external provider activation is
  established by this draft.
