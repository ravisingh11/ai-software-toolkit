# Migrating from Guardrails to Proof

The Guardrails component is now named **Proof**. The rename is a hard cutover:
the runtime, workflows, installer, and `ai-toolkit` CLI read only the Proof
names. Nothing falls back to a Guardrails path or variable, and a missing
`PROOF_*` variable reports an unconfigured producer, never a pass.

Evaluation semantics, control IDs, evidence schemas, policy modes, and the
advisory/enforced behavior of every control are unchanged.

## What changed

| Guardrails | Proof |
| --- | --- |
| `.guardrails/` installed runtime and configuration | `.proof/` |
| `GUARDRAILS_*` repository variables | `PROOF_*` (for example `PROOF_BUILD_COMMAND`) |
| `.github/workflows/guardrails-scorecard.yml` | `.github/workflows/proof-scorecard.yml` |
| `.github/workflows/guardrails-scorecard-badge.yml` | `.github/workflows/proof-scorecard-badge.yml` |
| `Guardrail Scorecard` check | `Proof Scorecard` check |
| `guardrails-badge.svg` Pages badge | `proof-badge.svg` |
| `guardrails-*` artifacts and `guardrails:` check external IDs | `proof-*` and `proof:` |
| `.artifacts/guardrails/` local scan output | `.artifacts/proof/` |
| `toolkit.toml` `[guardrails]` table and `guardrails` component | `[proof]` table and `proof` component |
| `# Guardrails v2 installer-owned ...` ownership markers | `# Proof installer-owned ...` |

Other check names, such as `Build`, `Unit Tests`, and `PR Change Scope`, do not
change.

## 1. Let the installer print your migration

Run the installer from a toolkit checkout that includes the rename, against
your repository:

```sh
python3 /path/to/ai-software-toolkit/tooling/install.py --target . --refresh-existing --dry-run
```

It refuses to write anything while a Guardrails layout is present and prints
the exact commands for your installation. A GitHub-profile installation with
the badge publisher prints steps like these:

```text
mkdir -p .proof
git mv .guardrails/change-scope.yaml .proof/change-scope.yaml
git mv .guardrails/documentation.yaml .proof/documentation.yaml
git mv .guardrails/ground-truth-ai.yaml .proof/ground-truth-ai.yaml
git mv .guardrails/policy.yaml .proof/policy.yaml
git mv .guardrails/pr-metadata.yaml .proof/pr-metadata.yaml
git mv .guardrails/providers.yaml .proof/providers.yaml
perl -pi -e 's#\.guardrails/#.proof/#g; s/guardrails([-:])/proof$1/g; s/GUARDRAILS_/PROOF_/g; s/Guardrails /Proof /g' .proof/providers.yaml
git rm -r -q .guardrails
rm -rf .guardrails
git rm .github/workflows/build.yml
git rm .github/workflows/guardrails-scorecard.yml
...
python3 <toolkit>/tooling/install.py --target . --refresh-existing --scorecard-badge
```

Run them in order. The moves keep your policy, documentation and ground-truth
mappings, change-scope and PR-metadata settings, and provider selections. The
`perl` step rewrites Guardrails paths, artifact prefixes, and variable names
inside those preserved files and, when present, in a `.pre-commit-config.yaml`
generated by `--local-hooks`. `rm -rf` clears ignored leftovers such as
`__pycache__` that `git rm` keeps. The installer-owned runtime and workflows are
removed and reinstalled under the Proof names. Workflows you own, which lack
the installer marker, are left alone; review them for `GUARDRAILS_` or
`.guardrails/` references yourself.

If you edited an installer-owned workflow, reapply the edit to the reinstalled
workflow; `git diff` against the removed file shows it.

Guardrails v1 installations still need the clean reinstall described in the
[v1.0.0 release notes](../releases/v1.0.0.md).

## 2. Update `toolkit.toml` and renamed skills

If you use the `ai-toolkit` CLI, it rejects a Guardrails `toolkit.toml`.
Rename the `[guardrails]` table to `[proof]`, the `"guardrails"` entry in
`components` to `"proof"`, and each `.guardrails/` path to `.proof/`.

The `change-guardrail-control` skill is now `change-proof-control`.
`ai-toolkit update` refuses to run while the old skill is installed and prints
its replacement, for example:

```text
git rm -r -q --ignore-unmatch .agents/skills/change-guardrail-control
rm -rf .agents/skills/change-guardrail-control
ai-toolkit skills install --skill change-proof-control --client codex
```

Then run `ai-toolkit update` to refresh `toolkit.lock.json`.

## 3. Rename repository variables

Copy each `GUARDRAILS_*` variable to its `PROOF_*` name. Keep the old variables
until no open branch still runs Guardrails workflows, then delete them:

```sh
for name in $(gh variable list --json name --jq '.[].name | select(startswith("GUARDRAILS_"))'); do
  gh variable set "PROOF_${name#GUARDRAILS_}" --body "$(gh variable get "$name")"
done
```

```sh
for name in $(gh variable list --json name --jq '.[].name | select(startswith("GUARDRAILS_"))'); do
  gh variable delete "$name"
done
```

Environment variables for local scans change the same way, for example
`PROOF_BUILD_COMMAND` and `PROOF_WORKING_DIRECTORY`.

## 4. Update required checks and badges

- If a ruleset requires `Guardrail Scorecard`, remove it before merging the
  migration and require `Proof Scorecard` after it reports on a pull request.
- Replace `guardrails-badge.svg` links with `proof-badge.svg`. The badge
  publisher stops updating the old file.
- Update links to the `guardrails-scorecard.yml` workflow badge.

## 5. Verify

```sh
python3 .proof/doctor.py
python3 .proof/scan.py
```

Then open a pull request and confirm the `Proof Scorecard` check reports.
`doctor` reporting **configured** is not evidence that a check ran.
